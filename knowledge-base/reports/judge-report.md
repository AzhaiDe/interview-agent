# 严格盲审报告

审查命令：`npm run kb:judge`  
审查原则：证据优先、重复不计数、没有独立专家盲审不升级评分锚点。

## 结论

**当前数据不能整体标记为 `verified`。** 本次严格审查只确认了 4 条官方技术文档来源可标记为 `verified`；其余 22 条社交平台来源保留为 `candidate`。派生知识条目全部保留为 `pending_expert_review`。

这不是程序失败，而是发现了真实的内容质量问题：当前生成器为了满足数量，重复循环少量概念和问题模板，不能把它们当成 150 个独立概念或 300 个独立问题。

## 发现的问题

| 问题 | 数量 | 处理 |
|---|---:|---|
| `DUPLICATE_CONTENT` | 1,241 | 在 `judged/` 中标记，运行时不得按独立条目计数 |
| `SYNTHETIC_VARIANT` | 312 | 标记为自动变体，必须拆成有独立定义、反例、版本和来源的真实子概念 |
| `NO_BLIND_RATERS` | 450 | 评分锚点继续待审，需两名专家独立评分并计算 Kappa/ICC |

## 已完成的修复

- 所有派生条目现在都携带官方文档来源或候选面经来源，修复了原先仅依赖论坛来源的问题。
- 误区条目补充了反例字段。
- 故障条目保留诊断和缓解步骤，满足运行手册的最低字段要求。
- 新增 `knowledge-base/judged/`，将审查状态和问题写入独立产物，避免覆盖原始种子。
- 运行时应优先读取 `judged/*.jsonl`，过滤 `judge_status=verified`；`pending_expert_review` 不得直接用于自动评分。

## 为什么没有强行全部盖章

当前条目的定义大量使用“围绕 X 的定义、机制、边界、指标与故障处理”这类生成式占位描述；它们没有逐条给出技术事实、适用版本、反例、指标基线和独立来源。评分锚点也没有真实候选答案、专家评分和一致性统计。把这类条目标成 `verified` 会直接污染 Agent 的面试判断。

## 完成最终验收所需的最小工作

1. 删除或重写 312 个自动概念变体，补成独立子概念。
2. 对重复问题和追问做问题族去重，每个问题保留真实来源和预期信息增益。
3. 每岗位邀请至少两位专家盲审，并记录 `expert_rater_ids`、评分、理由和 Kappa/ICC。
4. 通过盲审的条目才把 `judge_status` 与 `status` 升级为 `verified`。
5. 再运行 `npm run kb:validate && npm run kb:judge`，并检查重复率和来源覆盖率。
